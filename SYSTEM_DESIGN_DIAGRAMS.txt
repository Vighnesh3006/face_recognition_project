8.3  UI FLOW DESIGN
--------------------------------------------------------------------------------

  The UI Flow Design illustrates how a user navigates through the GestureOS
  graphical interface, which is built as a single-window Tkinter application
  with a persistent sidebar containing five navigation pages. The flow begins
  at the Control page — the default landing page — and branches based on user
  intent: starting a session, registering a new user, remapping gestures,
  adjusting settings, or reviewing logs. Each page has its own internal
  workflow; for example, the Users page walks through a five-angle camera
  capture process before registration, and the Control page drives the
  two-phase session lifecycle (authentication then gesture control). All
  configuration changes made through the GUI are immediately persisted to
  system_config.json, ensuring settings survive application restarts.

8.6  DATA FLOW DIAGRAMS
--------------------------------------------------------------------------------

  The Data Flow Diagrams (DFDs) describe how data moves through the GestureOS
  system at three levels of abstraction. At Level 0, the system is treated as
  a single black box receiving webcam frames and user gestures as input and
  producing OS-level actions, configuration writes, and log entries as output.
  At Level 1, the system is decomposed into six major processes — preprocessing,
  face authentication, hand gesture detection, safety and stability, action
  execution, and logging — showing how data stores (the config JSON, face
  encoding pickles, and the activity log) interact with each process. At Level
  2, the two most complex processes are expanded further: gesture detection is
  broken into MediaPipe detection, feature extraction, finger counting, ML
  classification, and rule-based fallback; face authentication is broken into
  the frame quality gate, HOG face detection, ResNet encoding, and distance
  comparison. Together the three levels provide a complete, layered picture of
  every data transformation in the system.

8.6.1  DFD Level 0 — Context Diagram
──────────────────────────────────────

  The Level 0 Context Diagram presents the entire GestureOS system as a
  single process bubble surrounded by its four external entities: the webcam
  (which provides raw BGR video frames), the registered user (who presents
  their face and performs hand gestures and receives OS-level feedback), the
  unregistered user (whose gesture attempts are silently blocked), and the
  operating system and file system (which receive keyboard/hotkey events,
  media commands, and brightness adjustments, and store configuration, logs,
  and recordings respectively). This diagram establishes the system boundary
  and identifies all external interfaces without exposing any internal
  processing detail.

8.6.2  DFD Level 1 — Main Processes
─────────────────────────────────────

  The Level 1 DFD decomposes the system into six numbered processes connected
  by data flows. Process 1.0 (Preprocessing) receives raw frames from the
  webcam and applies CLAHE lighting normalisation, horizontal flipping, and
  resizing before distributing enhanced frames to both downstream processes.
  Process 2.0 (Face Authentication) runs in a background thread every two
  seconds, comparing a live face encoding against stored encodings from data
  store D3, and feeding an auth result (True/False) into the safety layer.
  Process 3.0 (Hand Gesture Detection) uses MediaPipe to extract 21 landmarks
  per hand and classifies the gesture using either the SVM model from data
  store D2 or the rule-based fallback, producing a gesture label and confidence
  score. Process 4.0 (Safety and Stability) acts as a gatekeeper, applying
  the 3-frame stability buffer, hold-to-confirm timer, danger hold timer,
  cooldown, and auth check before passing a confirmed gesture to Process 5.0
  (Action Execution), which dispatches the appropriate OS command. All
  significant events are written to the activity log by Process 6.0 (Logging).

8.6.3  DFD Level 2 — Gesture Detection (Process 3.0) Expanded
───────────────────────────────────────────────────────────────

  The Level 2 DFD expands both Process 3.0 (Gesture Detection) and Process
  2.0 (Face Authentication) to their internal sub-processes. For gesture
  detection, the enhanced frame first passes through sub-process 3.1
  (MediaPipe Hand Detection) configured with model_complexity=1 and
  max_num_hands=2, which outputs up to 42 normalised 3D landmarks and
  handedness labels. Sub-processes 3.2 (Feature Extraction) and 3.3 (Finger
  Counting) run in parallel: feature extraction builds the 126-dimensional
  normalised vector used by the ML classifier, while finger counting applies
  the palm-scale 3-cue majority vote algorithm independently for direct count
  comparisons. Sub-process 3.4 (ML Classifier) queries the SVM model stored in
  the gesture model pickle file; if confidence falls below 0.75, sub-process
  3.5 (Rule-Based Fallback) takes over using shape detectors and palm zone
  logic. For face authentication, sub-process 2.1 (Quality Gate) rejects
  blurry or dark frames before the frame is resized and passed through 2.2
  (HOG Detection), 2.3 (ResNet Encoding), and 2.4 (Distance Comparison) against
  stored face encodings.

8.7.1  CLASS DIAGRAM
--------------------------------------------------------------------------------

  The Class Diagram shows the six main classes of the GestureOS system, their
  attributes, methods, and inter-class relationships. ConfigManager sits at the
  centre of the dependency graph as it is used by all other classes; it manages
  user profiles, gesture-to-action mappings, and system settings, persisting
  everything to a JSON file with hot-path caching for performance-critical
  attributes. GestureController is the largest and most complex class,
  containing the MediaPipe hand detection pipeline, the palm-scale finger
  counting algorithm, the ML and rule-based gesture classifiers, the
  hold-to-confirm and danger hold timer logic, the action executor, and the
  OpenCV camera loop. FaceAuthenticator handles all identity-related
  operations: multi-angle CNN registration, CLAHE-enhanced HOG live detection,
  frame quality gating, and non-blocking background re-authentication with the
  4-second wall-clock timeout. ActivityLogger provides thread-safe timestamped
  event logging. ScreenRecorder manages background screen capture. GestureTrainer
  encapsulates the SVM training pipeline and model persistence. The
  GestureControlGUI class (from gui_app.py) creates and owns instances of all
  other classes, acting as the composition root for the application.

  The Use Case Diagram identifies three distinct actors and sixteen use cases
  that describe all functional interactions with the GestureOS system. The
  Registered User (an authenticated person with a stored face encoding) is the
  primary actor and can perform all gesture-based actions after passing face
  authentication. The Unregistered User represents anyone not in the system;
  their only interaction is UC9 (Attempt Gesture), which the system blocks and

  UC2 (Control PC) which includes UC1 (Authenticate) — meaning gesture control
  is impossible without prior face authentication — and UC8 (Shutdown/Restart)

  UC14 (Collect Data) as a prerequisite, reflecting the two-step training
  workflow enforced by the system.

8.7.3  SEQUENCE DIAGRAMS
--------------------------------------------------------------------------------

  Three sequence diagrams are provided to capture the most important
  time-ordered interactions between objects in the system. The Authentication
  Sequence shows the message flow from the user clicking Start Session through
  the GUI creating a GestureController, the controller opening the camera,
  spawning parallel auth workers every 0.35 seconds, and the FaceAuthenticator
  performing HOG detection, ResNet encoding, and distance comparison until a
  registered face is confirmed — at which point the welcome screen is shown and
  the gesture worker thread is started. The Gesture-to-Action Sequence traces
  a single gesture (three fingers raised) from the raw camera frame through
  MediaPipe detection, SVM classification, three-frame stability buffering,
  hold-timer confirmation, action execution via pyautogui, and final logging.
  The Face Absence Sequence demonstrates the security mechanism: as the user
  leaves the frame, the background auth thread increments failure counts, a
  visual warning appears after one second of absence, and after four seconds
  the timeout logic sets auth_result to False, causing the gesture worker to
  stop the session and the GUI to reset to idle state.

8.7.5  STATE CHART DIAGRAM
--------------------------------------------------------------------------------

  The State Chart Diagram models the discrete states of the GestureController
  object and the valid transitions between them. The system starts in the IDLE
  state and transitions to AUTHENTICATING when the user clicks Start Session,
  during which the camera opens and auth workers are spawned. A successful
  face match transitions the system to GESTURE CONTROL (ACTIVE), the primary
  operational state where gesture detection, action execution, and background
  re-authentication all run concurrently. From this state, holding the
  count_10 gesture for five seconds with sufficient confidence triggers a
  transition to SHUTDOWN COUNTDOWN, a three-second timed state that can be
  cancelled by dropping the hand (returning to GESTURE CONTROL) or completes
  to invoke a system shutdown. Any exit condition — Q key, face absent for
  four seconds, or manual stop — transitions through the CLEANUP state
  (releasing the camera and writing the final log entry) and back to IDLE.
  Sub-states within GESTURE CONTROL are also shown, including DETECTING,
  HOLDING, FIRING, COOLDOWN, FACE_WARNING, and DANGER_HOLDING, providing
  complete coverage of the system's runtime behaviour.

8.7.6  COMPONENT DIAGRAM
--------------------------------------------------------------------------------

  The Component Diagram illustrates the modular architecture of GestureOS
  as a layered set of software components and their dependencies. The
  Presentation Layer (gui_app.py) sits at the top and provides the five-page
  user interface; it depends on all layers below it but no layer depends on it,
  making it independently replaceable. The Core Engine (gesture_control.py)
  forms the central processing layer and houses three internal sub-components:
  MediaPipe Hand Detection, the ML Classifier (SVM via scikit-learn), and the
  Rule-Based Detector. Below the core engine, four parallel service layers
  operate independently: the Identity Layer (face_auth.py) handles all
  face-related operations; the Config Layer (config_manager.py) manages
  persistent settings; the Log Layer (logger.py) handles activity recording;
  and the ML Training component (gesture_trainer.py) manages model lifecycle.
  The Recording Layer (screen_recorder.py) provides screen capture. All
  components interface with three external systems at the bottom: the Windows
  OS (for keyboard, scroll, and system commands), the Webcam Device (for video
  capture), and the File System (for all persistent storage). This layered
  structure ensures that changes to one layer have minimal impact on others.

8.7.7  DEPLOYMENT DIAGRAM
--------------------------------------------------------------------------------

  The Deployment Diagram describes the physical and software infrastructure
  on which GestureOS runs. The entire system is deployed on a single Windows
  10/11 PC — there are no servers, no cloud services, no network dependencies,
  and no external APIs. Within the PC, the Python 3.10 runtime hosts the
  GestureOS application alongside its key library dependencies: MediaPipe
  0.10.9 (which ships with its own pre-trained hand landmark models embedded
  in the package), face_recognition 1.3.0 (backed by dlib's HOG detector and
  ResNet face embedding model), scikit-learn 1.3.2 (providing the SVM
  classifier and StandardScaler), and pyautogui with pywin32 (for OS-level
  action dispatch). All persistent artefacts — configuration, face encodings,
  gesture training data, ML models, the activity log, and screen recordings —
  are stored in the local file system with no encryption, making them directly
  accessible for inspection and backup. Two physical devices connect to the PC:
  the USB or built-in webcam (the sole sensor input) and the monitor (which
  receives brightness adjustment commands). This single-node, fully offline
  architecture is a deliberate design choice that maximises privacy, eliminates
  latency from network calls, and ensures the system works without internet
  access.
